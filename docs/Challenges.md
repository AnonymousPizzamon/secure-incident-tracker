The core security concern here is access control, which maps directly to OWASP A01:2021 (Broken Access Control), the most common vulnerability class in modern web apps. I treat authentication and authorization as two separate problems: once a user logs in, their JWT proves who they are on every request, but it says nothing about what data they're allowed to touch. A common attack is to tamper with the jwt in the request by changing the username inside, I guard against this by making sure the HMAC matches, if it doesn't match, then they tampered with the JWT, and so the token is rejected. The reason they can't forge it successfully is because they will never know the secret key that was used to form the JWT (it lives on server or cloud through secrets, etc..).
The subtler and more dangerous version is an Insecure Direct Object Reference, where an attacker who is already a legitimate, authenticated user keeps their own valid token but manipulates a parameter in the url like a user id or record id, hoping the backend will hand back another user's data. That only works if the server trusts identity supplied by the client, which is exactly the mistake I designed against: instead of reading a user id from the request, I derive the current user server-side from the verified JWT and look up their actual record, then scope every event query to that user. Because identity comes only from the signed token and ownership is enforced in the backend query rather than the frontend, a user can change whatever they want in the header or body and still never reach data that isn't theirs.
